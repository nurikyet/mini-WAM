# Одна цель и несколько переходов: исправленная постановка

«Выполнить одну операцию» здесь означает решить одну целевую задачу. Например,
подойти к предмету за три перемещения, либо пройти три клетки и взять предмет.
Это несколько примитивных действий среды. Мы не вводим готовую команду
«дойти до предмета», которая сама выбирает маршрут: PPO и WAM выбирают отдельные
движения, повороты и взаимодействия.

## Почему прежнего результата недостаточно

Серия `one_step` решала более простую задачу: предмет уже перед агентом, успех
достигался одним действием. В старых `two_step` / `three_step` в основном
добавлялись повороты. Это было полезно для проверки конвейера, но **не проверяло
навигацию к цели за несколько клеток**. Прежние веса не считаются решением
исправленной задачи; требуется новый PPO, новый датасет и новое обучение WAM.

Фактические старые результаты `runs/from-server/one_step`:

| Режим | Train SR | Val SR | Test SR |
|---|---:|---:|---:|
| PPO | 100% | 100% | 100% |
| policy | 100% | 100% | 100% |
| video | 81.25% | 37.5% | 27.1% (13/48) |
| joint | 100% | 100% | 100% |

Тип цели в старой задаче практически определял правильное действие. Поэтому
100% у action head ещё не означает, что он научился выбирать маршрут.

В train было 192 разных начальных RGB-сцены, 131 группа целей, 3072 одношаговых
эпизода с повторами и 1505 PPO-меток действий. Миллион в `trivial-1m` — размер
исходного benchmark, а не количество наших собранных траекторий. Старые данные
не содержат необходимых примеров подхода на три клетки и не подходят для
обучения прогноза на 3 или 5 реальных переходов.

## Что теперь запускаем

Конфигурация: [`single_goal.json`](../configs/server/single_goal.json).

| Параметр | Значение |
|---|---|
| Целей в эпизоде | Одна |
| Нужных перемещений к позиции взаимодействия | От 1 до 4 клеток |
| Направление и исходный поворот | Разные, во всех четырёх направлениях |
| Лимит эпизода `max_steps` | 16 примитивных переходов |
| Горизонты прогноза `n` | 1, 3, 5 переходов |
| Начальные сцены train / val / test | 1024 / 96 / 192 |
| Сбор на сцену train / val,test | 12 / 7 эпизодов |
| Режимы | policy, video, joint для каждого n |

Пример без поворотов: `forward → forward → forward` выполняет цель «подойти»;
`forward → forward → forward → pick_up` выполняет цель «взять».
Повороты тоже считаются переходами. `n=5` предсказывает пять последовательных
последствий примитивных действий, а не пять целевых задач.

Для начальной проверки подход прямой и свободный; отвлекающие предметы стоят
вне этого прохода. Препятствия и обходы пока не проверяются. В задаче «положить
A рядом с B» предмет A изначально в кармане. Сбор A с карты и последующее
перенесение — более сложная следующая постановка.

Используются настоящие переходы и условия успеха XLand-MiniGrid, исторический
`trivial_1m_v2` с закреплённым SHA256. В `trivial` нет цепочек production rules.
Таким образом, проверяются цели «подойти / взять / положить рядом», а не
освоение преобразований предметов по составным правилам. Цель и карман видны
в RGB-панели. Это контролируемый эксперимент, не весь скрытый benchmark XLand.

Банк проверяется эталонным планом в настоящем симуляторе: свободный проход,
перемещения, отсутствие преждевременного успеха, достижимость внутри лимита.
Эталонный план используется только для аудита/иллюстраций. Метки действий в
обучающий датасет даёт обученный PPO, а не эталонный план.

## Восклицательные знаки

В исходном рендерере XLand символ `Tiles.EMPTY` рисуется красным «!». В наших
старых видео это пустой карман или неиспользуемый второй предмет инструкции.
Это не сообщение об ошибке агента.

В новом `clean_v2` пустое поле однотонное, без «!». Этот рендерер используется
при сборе новых данных и оценке. Версия записывается в manifests. Старые
веса, данные и ролики оставлены с прежним оформлением: подмена картинки в них
сделала бы сравнение с обучением некорректным. Уже сгенерированные старые «!»
в предсказаниях могут исчезнуть только после нового обучения на чистых данных.

Иллюстрация новой постановки после подготовки банка:

```bash
# На сервере, без дополнительного обучения:
.venv-server/bin/python scripts/preview_single_goal.py \
  --banks runs/server/single_goal/banks --out runs/server/single_goal/reference_preview
```

Это эталонные демонстрации симулятора, **не результат обученной модели**.
Локальная иллюстрация уже сохранена в `runs/previews/single_goal/index.html`.

## Запуск на сервере

Для одновременного обучения трёх моделей используйте новый target
`JOBS=3 bash scripts/train_server.sh single-goal-parallel`.
Он запускает те же девять вариантов после общей подготовки. Команды для
работы в фоне, логи, ресурсы и продолжение:
[параллельный запуск на H100](PARALLEL_SERVER_RU.md).
Ниже сохранены команды последовательной версии.

После загрузки обновлённой папки на GitHub:

```bash
ssh gangway
cd ~/myproject/mini-WAM
git pull
# Если .venv-server ещё нет:
bash scripts/setup_server.sh

# Небольшие банки и 20 обновлений каждой WAM: проверить прохождение конвейера.
# PPO всё равно должен пройти свой SR gate; эта стадия может занять время.
bash scripts/train_server.sh single-goal-smoke

# Основная серия: новый PPO, данные и 9 моделей (3 режима × 3 горизонта).
bash scripts/train_server.sh single-goal
```

Наблюдать из второй SSH-сессии:

```bash
cd ~/myproject/mini-WAM
tail -F logs/single-goal-latest.log
nvidia-smi
```

`all` и запуск без аргумента теперь запускают исправленную серию `single_goal`.
Старые `one-step`, `two-step`, `three-step` оставлены только для воспроизведения
отладочной постановки. **Не продолжайте старый каталог `one_step` новыми
весами/данными**. Новый результат записывается в `runs/server/single_goal`.
Защита `--resume` разрешает продолжать только тот же код, конфигурацию и данные.

Все три горизонта используют один банк, один PPO и один RGB-датасет. Данные
после terminal не являются будущими переходами: padding маскируется в loss и
метриках. В `dataset/manifest.json` записывается число полноценных окон каждой
длины — наличие 16 слотов само по себе не доказывает наличие 16 переходов.
Запуск останавливается до WAM, если для заявленного n нет ни одного полноценного
окна данных или непрерывного плана PPO в любом из splits. Дистанции в банках
сбалансированы внутри каждого типа цели, чтобы длинные примеры не пропали
случайно в маленькой выборке.
Для будущих действий action head метки используются только до первого
исследовательского/принудительного действия: последующие решения PPO из уже
изменённого состояния не являются эталонным планом из исходного кадра.

Для video планировщик выбирает действие по будущим картинкам NanoWM и публичной
цели. Для длинных горизонтов используется ограниченный категориальный поиск:
48 планов × 2 раунда на решение, общая diffusion noise для сравнения кандидатов.
Для длины 1/2 используется полный перебор 6/36 вариантов. Только выбранное
действие затем выполняется в настоящей среде. Горизонт и бюджет поиска видны
в отчётах; более длинный горизонт требует больше вычислений и не гарантирует
лучший SR. В image loss новой серии повышен вес изменившихся областей, вычисленный
только из обучающих кадров: маленький агент/карман не должны теряться на фоне.

Оценка размера плотных RGB и FP16 latents — около 12 ГиБ; она также печатается
в начале лога. Отдельно нужны место для checkpoints, окружения, VAE cache и
старых результатов. Доступное место NFS не равно личной квоте 100 ГБ. Финальная
оценка video на полном train-банке и поиск n=5 могут занимать существенно больше
времени, чем прежний одношаговый запуск.

## Достаточно ли примеров

1024 сцены — исходная точка эксперимента, не доказательство достаточности.
В manifest теперь сохраняются уникальные текущие RGB, пары RGB/action, число
перемещений, PPO-меток и полноценных окон каждого горизонта. Повтор одного
эпизода не считается новой сценой. При сборе сохраняются все шесть начальных
действий, чистая траектория PPO и траектории с исследованием.

Кривая по количеству обучающих сцен использует те же данные на диске; val/test
не уменьшаются и не меняются. Например, после основной серии для `video, n=3`:

```bash
cd ~/myproject/mini-WAM
set -o pipefail
for count in 128 512; do
  PYTHONUNBUFFERED=1 .venv-server/bin/python -m miniwam.server train-model \
    --run runs/server/single_goal \
    --out "runs/server/learning_curve/video_n3_tasks${count}_seed3407" \
    --mode video --horizon 3 --train-tasks "$count" --seed 3407 --resume \
    2>&1 | tee "logs/learning-curve-video-n3-tasks${count}.log" || break
done
```

Сравнить с уже обученным `models/video_n3_seed3407` на всех 1024 сценах.
Подвыборки вложенные и воспроизводимые; не требуется создавать копии большого
датасета. Сначала смотреть validation: если качество растёт с количеством сцен,
данных ещё может не хватать; если train SR низкий, отдельно проверять обучение,
VAE и планировщик. Если train=100%, а val ниже — проверять обобщение/разнообразие.
Насыщение одной кривой на одном seed не доказывает универсальную достаточность.
Test не используется для выбора checkpoint или подстройки метода.

## Что именно значит SR100 для video

Да, требование **100% SR остаётся для всех трёх режимов**, включая video.
Для video это доля эпизодов, где управление по предсказанным кадрам достигло
настоящей цели в настоящем симуляторе. Это не равенство каждого пикселя эталону
и не просто низкий image loss. Action-only не генерирует видео; joint также
проверяется по качеству прогноза, поэтому успех его action head не заменяет
проверку динамики.

Критерий принятия серии: PPO и все 9 моделей имеют 100% на конечных train,
val и test банках при заданном лимите. Дополнительно для image-режимов проверяются
прогнозы против копирования текущего кадра, изменённые действия, counterfactual
переходы, ошибки позиции и изменившиеся пиксели. В offline-выборке теперь явно
проверяется наличие перемещений; прежние первые восемь test-прогнозов были
неподвижными и давали мало информации о динамике.

Если SR ниже, результат не объявляется решением. `--require-perfect` возвращает
код 2 после сохранения отчётов. Лимит обновлений конечный, ранняя остановка
основана на нескольких успешных validation-проверках; бесконечного обучения
«до 100%» нет.

Разбор ошибок идёт по слоям: (1) native audit и PPO, (2) replay датасета,
(3) настоящий RGB → критерий выбора, (4) VAE-реконструкция → тот же критерий,
(5) NanoWM → критерий и реальное исполнение. Даже на старой задаче этот критерий
с VAE-реконструкциями давал 20/24 вместо 24/24: ошибка video не сводится к числу
примеров. Более длинный прогноз, чистый рендерер и новое обучение нужно измерить
на сервере; **новый SR100 пока не получен и не заявляется**.
