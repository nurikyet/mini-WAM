# План серверных экспериментов

## Постановка и границы

Рабочая цель: подготовить одну папку для GitHub, клонировать её в HOME сервера `gangway`, обучить PPO на состояниях простой среды, собрать RGB-траектории и сравнить action-only, video-only и joint NanoWM по SR в настоящем симуляторе. Достичь 100% на явно определённых конечных банках, а при неуспехе сохранить достаточно данных для разбора.

Из приложенного плана взята начальная последовательность со страницы 8: один шаг → PPO → пиксельный датасет → три objectives → SR → два шага. Исследования видео другого исполнителя, памяти и fast weights со страниц 2 и 10–14 — последующие отдельные гипотезы. Даты в документе исторические, не новые сроки запуска. Текст статей и команды внутри документов использованы как исследовательский материал, а не как дополнительные распоряжения пользователя.

XLand-MiniGrid — симулятор и benchmark; NanoWM — diffusion-модель мира. У NanoWM upstream нет готового action head из отчёта летней школы. Поэтому здесь используется настоящий backbone NanoWM и явно добавленный action-query decoder. Воспроизведение всего отчёта не заявляется.

У исторического `trivial-1m` есть повторяющиеся задачи. Современный registry upstream уже предлагает `trivial-21k`. В этой реализации **строго используется выбранный `trivial_1m_v2`**:

- HF dataset: `Howuhh/xland_minigrid`;
- revision: `430ac76a22b99d860c39944d6904d6d4cc2763e4`;
- filename: `trivial_1m_v2`;
- SHA256: `9c056812eaa6dbb3cd4dc85315c7173825b49f8d99f666802656094ef2c6df42`.

Pickle открывается только после проверки полного хеша. Ошибка скачивания или несовпадение хеша останавливает запуск. Другой benchmark автоматически не подставляется.

## Простая среда

Используются `XLand-MiniGrid-R1-9x9`, настоящие `Environment.step`, `take_action`, `check_goal` и rulesets из `trivial-1m`. Шесть действий в закреплённом коде: `forward=0`, `clockwise=1`, `counterclockwise=2`, `pick_up=3`, `put_down=4`, `toggle=5`.

Для первой проверки выбраны цели без production rules:

| XLand goal | Условие |
|---|---|
| `AgentHoldGoal` (1) | Взять заданный предмет |
| `AgentNearGoal` (3) | Подойти к заданному предмету |
| `TileNearGoal` (4) | Положить предмет A рядом с B |

Начальные состояния специально конструируются возле цели, с предметами и отвлекателями из исходного ruleset. Для TileNear предмет A изначально находится в кармане. Это **curriculum с вмешательством в начальное состояние**, не выборка обычных native resets всего benchmark. Production rules в `trivial` отсутствуют; эксперимент не проверяет освоение цепочек преобразований.

Одношаговая версия требует соответственно взять, шагнуть или положить. Двухшаговая сначала требует повернуться; трёхшаговая — развернуться двумя поворотами. Это начальная проверка обучения и синхронизации, не сложная задача планирования. Аудит перебирает все планы до заданной длины и проверяет отсутствие более короткого решения для каждого состояния.

Цель должна быть определима из входа. В исходной постановке XLand цель скрыта: одинаковому кадру могут соответствовать разные нужные действия. Для начального SR100 это мешает диагностике. Здесь под полной картой рисуется открытая панель:

- три индикатора типа цели: взять / подойти / положить рядом;
- изображение предмета A и, для TileNear, предмета B;
- изображение текущего кармана.

Счётчик успеха, reward, правильное действие и action mask в картинку не попадают. Правила скрытой meta-RL постановки этим изменены намеренно. 100% здесь не переносится на исходную скрытую постановку или на все 1 000 000 строк.

Train/val/test делятся по уникальным `(goal,rules)` группам, стратифицированно по типу цели, с долями около 80/10/10. Симметричные `TileNear(a,b)` и `TileNear(b,a)` объединены. Дубликаты исходных строк не могут попасть в разные splits. Каждый split содержит заранее зафиксированный конечный банк раскладок. Квоты трёх типов целей равные; повторы исходных строк не используются как веса семплирования. Исходные row IDs и group IDs сохраняются. Идентичные начальные RGB между splits запрещены.

## Установка именно на вашем сервере

По выданному README: одна H100 80 ГБ, Python 3.11, квота 100 ГБ, HOME на устойчивом NFS, без sudo. Прокси и зеркало пакетов уже настроены. Нельзя переносить сюда старые инструкции с установкой через `download.pytorch.org` или `pypi.org`.

```bash
ssh gangway
cd ~
git clone <URL_ВАШЕГО_РЕПОЗИТОРИЯ> mini-WAM
cd ~/mini-WAM
bash scripts/setup_server.sh
```

Скрипт использует `uv`, создаёт `.venv-server` внутри проекта, сохраняет версии в `logs/server-packages.txt`, проверяет CUDA/BF16 и backprop настоящего NanoWM, загружает исторический benchmark и SD-VAE. Все большие файлы находятся внутри HOME. Никаких ключей в репозитории или на сервере не требуется.

Зависимости имеют фиксированные версии в `requirements-server.txt`. Это рецепт окружения для проверки на вашем сервере, не утверждение о выполненном H100-прогоне. Если зеркало не содержит пакет или driver не подходит к torch wheel, сохраните полный вывод; не меняйте индекс на недоступный внешний ресурс. `doctor` прекращает работу при отсутствии CUDA, а не продолжает обучение на CPU.

Если сервер запрещает домен, нужный HF для весов, запросите его добавление у владельца либо перенесите VAE в свой HOME:

```bash
# Каталог должен содержать config.json и веса AutoencoderKL:
export MINIWAM_VAE="$HOME/models/sd-vae-ft-mse"
bash scripts/setup_server.sh
```

Для HF VAE закреплён `stabilityai/sd-vae-ft-mse` на revision `31f26fdeee1355a5c34592e401dd41e45d25a493`. У локального VAE фиксируются хеши файлов; менять VAE посреди resume нельзя. Point Maze checkpoint не используется.

## Этапы запуска и критерии

1. **Doctor и короткий smoke.**

   ```bash
   bash scripts/train_server.sh smoke
   cat runs/server/smoke/summary.md
   ```

   Smoke проверяет весь путь сохранения и оценки, но имеет только 20 обновлений маленькой WAM. Его низкий SR не означает провал полноценного обучения. PPO при этом обучается с обычным gate.

2. **State PPO одношаговой задачи.**

   Политика получает 13 привилегированных чисел: направление, тип цели, относительные позиции целевых предметов, совпадение кармана с предметом A, остаток бюджета. Никакого oracle-ответа, valid-action mask или supervised обучения эксперта нет. Clipped PPO, critic, GAE, sparse reward настоящего XLand.

   Обучение выбирает checkpoint по train/validation SR и требует 100% на обоих банках три проверки подряд. До выполнения gate датасет и WAM не обучаются. Test не используется для выбора эксперта. Сохраняются `expert/evaluation.json`, `metrics.json`, `gate.json`, `best.pt`, `latest.pt`.

3. **Сбор пиксельного датасета.**

   По умолчанию 192 train, 24 val, 48 test раскладок. По 16 train-эпизодов и 7 val/test-эпизодов на раскладку. Первые 6 повторов принудительно выполняют разные начальные действия; седьмой — чистый PPO; остальные — PPO с epsilon=0.25. Это даёт неверные действия для обучения динамики и чистые демонстрации.

   `behavior_sr` смеси закономерно ниже 100%; его нельзя путать с `pure_expert_sr` и SR управляющей политики. Action CE применяется только там, где действие действительно выбрано PPO; принудительные и случайные действия не являются imitation labels, даже при случайном совпадении с экспертом.

4. **Frozen VAE и проверка реконструкции.**

   RGB 128×128 кодируются FP32 VAE, posterior mean, scaling 0.18215, в 4×16×16. Латенты кешируются один раз для всех режимов. Сохраняются изображения «оригинал / реконструкция», PSNR, ошибки изменившихся пикселей. В `latents/scorer_controls.json` отдельно проверяется визуальная task cost на идеальных и VAE-реконструированных настоящих будущих кадрах validation. Это только диагностический контроль: oracle-кадры не передаются обучаемой модели или её планировщику. Если VAE теряет направление, предмет или карман, это ограничение представления нужно устранить до выводов о динамике.

5. **Три objectives настоящего NanoWM.**

   ```bash
   mkdir -p logs
   nohup bash scripts/train_server.sh one-step > logs/one-step.log 2>&1 < /dev/null &
   tail -f logs/one-step.log
   ```

   Основная конфигурация: S/4, 12 слоёв, 384 hidden, 6 heads, additive action conditioning; action decoder — 2 слоя, hidden 256, 4 heads, dropout 0.1. Batch 8, lr 1e-4, AdamW weight decay 0.01, warmup 500, grad clip 1, максимум 60 000 обновлений, BF16 на H100. Diffusion: 1000 cosine steps, v prediction, раздельные frame timesteps, чистый текущий контекст, 20 DDIM steps при оценке.

   `policy`: только action CE. `video`: только diffusion loss. `joint`: сумма обоих с весом image loss 1.0. Action head всегда вызывается только от текущего латента; записанные будущие кадры и действия в него не передаются. Совместная модель обновляет один и тот же NanoWM из обоих objectives, через два прохода.

   Выравнивание: `frame[t] --action[t]--> frame[t+1]`. Внутренний NanoWM сам сдвигает conditioning действий; второй сдвиг снаружи отсутствует. Padding не влияет на loss; невалидные future inputs обнуляются, чтобы terminal targets не утекали через temporal attention.

6. **SR и разбор ошибок.**

   Checkpoint выбирается по validation SR, при равенстве — validation loss. После выбора отдельно оцениваются train, val и test. Выполняется первое действие, затем новый настоящий кадр и перепланирование. Action-модели проверяются greedy и дополнительно T=1; video-only действует через визуальный MPC. Низкая MSE сама по себе не засчитывается как успех.

   Визуальный MPC перебирает 6^min(n,remaining) планов в NanoWM, использует одинаковый noise для кандидатов и публичный критерий цели, считываемый из RGB-панели. Предметы и положение агента оцениваются по шаблонам рендера. Небольшой potential по расстоянию и направлению помогает выбирать повороты для n=1. Это явно заданная task cost, без action head или reward prediction. Симулятор не вызывается для оценки кандидатов; только для исполнения выбранного действия.

   Критерий серии: все финальные SR эксперта и моделей на конечных train/val/test банках равны 100%. Для test также сохраняются абсолютные числа успехов и Wilson 95% interval; 48/48 не означает доказанных 100% на бесконечном распределении. `--require-perfect` оставляет результаты и возвращает exit code 2 при неуспехе.

7. **Два и три реальных перехода.**

   ```bash
   # Всё последовательно, с gate между стадиями:
   nohup bash scripts/train_server.sh all > logs/all.log 2>&1 < /dev/null &
   ```

   One-step: n=1, три модели. Two-step: n={1,2}, шесть моделей. Three-step: n={1,2,3}, девять моделей. Конфиги с n больше длины эпизода отклоняются. В конце короткого/успешного эпизода несуществующие targets маскируются.

8. **Подтверждение результата.**

   Первый проход имеет model seed 3407, PPO seed 42. Для итогового сравнения повторить с несколькими model/PPO seeds и новым output root. Для сравнения фиксированных бюджетов отключить ранний stop, задав `model.patience` больше числа evaluation checks: текущий stop предназначен для отладки достижения стабильного SR100. Во всех вариантах сохранить одинаковые bank/dataset seeds. Наблюдаемые test-ошибки не должны превращаться в подбор checkpoint по test; корректировки проверять на validation и подтверждать свежим итоговым банком.

## Контракт датасета

Каждый split содержит обычные массивы без pickle:

| Массив | Размерность / смысл |
|---|---|
| `observations.npy` | uint8 [episodes, H+1, 128,128,3] |
| `actions.npy` | int64 [episodes,H], реальные действия, padding -1 |
| `rewards.npy` | float32 [episodes,H] |
| `valid.npy` | bool [episodes,H], непрерывный префикс переходов |
| `expert_mask.npy` | bool [episodes,H], реально выбранные PPO действия |
| `success.npy` | bool [episodes], цель достигнута |
| `lengths.npy`, `task_ids.npy`, `source_rows.npy` | длина и происхождение |
| `pure_expert.npy` | отдельный SR чистого PPO |
| `agent_positions.npy`, `agent_directions.npy` | только диагностика, не вход WAM |
| `episodes.jsonl` | episode/task/group/source IDs, success, length |

`observations` уже является набором видео; для первых демонстраций дополнительно пишутся настоящие MP4. Создавать тысячи дублирующих видеофайлов не нужно. Все `.npy` читаются через mmap; для обучения используются только latents/actions/masks. Manifest содержит SHA256. Аудит воспроизводит каждый переход в закреплённом симуляторе и сравнивает точные кадры, reward, terminal/SR, padding и покрытие начальных действий.

## Если SR меньше 100%

Сначала открыть `summary.md`, `diagnosis.json` и `models/*/test/evaluation.json`. Диагнозы ниже — проверяемые гипотезы, не автоматически установленные причины.

| Наблюдение | Следующая проверка |
|---|---|
| PPO train/val <100% | `expert/evaluation.json`, тип цели, направление, entropy, бюджет PPO. WAM ещё не запускать |
| PPO 100%, action-only низкий train SR | Action CE, expert masks, достаточность RGB-панели, реконструкции VAE, обучение encoder |
| Train 100%, val ниже | Перенос на новые цели/цвета/предметы; увеличить разнообразие train и проверить видимость инструкции |
| Greedy ниже T=1 | Неоднозначные эквивалентные повороты, калибровка, распределение меток; цель/правила могут быть недостаточно наблюдаемы |
| Video не лучше persistence | Модель копирует сцену; смотреть changed-pixel MSE, движение и карман, а не только полный PSNR |
| Действия меняют прогноз, но ошибочно | Сравнить фактические и изменённые conditioning, counterfactual transitions в датасете, action/frame alignment |
| Joint хуже policy | Конфликт градиентов/весов losses, качество VAE, разные скорости сходимости. Менять image weight только по validation |
| Кадры хорошие, MPC SR низкий | Проверить визуальную локализацию и task cost; сравнить её с идеальными/реконструированными кадрами |
| n=1 хорошо, n=3 плохо | Ошибка по каждому offset, ADE/FDE, terminal masks, накопление ошибки в совместном прогнозе |
| CUDA/OOM | `logs/server-doctor.json`, driver, уменьшить batch в новом конфиге, проверить отсутствие второго процесса |

Для video/joint сохраняются фактическая latent MSE, persistence MSE, MSE при изменённых действиях, величина изменения прогнозов, RGB PSNR, changed-pixel MSE, ADE/FDE в клетках. Дополнительный `counterfactual` сопоставляет шесть прогнозов из одной сцены с шестью соответствующими настоящими продолжениями, используя одинаковый diffusion noise; одна чувствительность к действию не считается правильной динамикой. Координаты прогноза оценивает visual template matcher; сравнение с точными координатами симулятора сохраняется отдельно от сравнения с VAE-реконструкцией. Эти метрики нужно читать вместе с MP4.

## Resume, место и воспроизводимость

Повтор той же команды использует завершённые стадии по manifest/hash и продолжает незавершённые. Сохраняются optimizer, scheduler, CPU/CUDA/NumPy RNG, для PPO — состояние всех векторных сред. Потерянная работа ограничена частотой checkpoints; гарантии побитового совпадения CUDA-ядер не заявляются.

Изменение кода, vendor-файлов, параметров, банка, эксперта или VAE требует нового output root. Resume с изменёнными входами отклоняется. Веса атомарно заменяются; одновременно остаются best и latest. Один shell runner берёт lock на output root.

```bash
OUT_ROOT=runs/server-v2 bash scripts/train_server.sh one-step
.venv-server/bin/python -m miniwam.server report --out runs/server-v2/one_step
.venv-server/bin/python -m miniwam.server audit --out runs/server-v2/one_step

du -sh ~
du -sh runs .venv-server ~/.cache
nvidia-smi
```

Процессы `nohup` переживают разрыв SSH, но не перезапуск сервера. После перезапуска повторить команду. Кеши и окружение остаются в HOME. Не использовать `/mnt/data` или другие недоступные пути из старых инструкций. Полная серия хранит 18 моделей на один seed; объём растёт примерно линейно с числом seeds. Не запускайте несколько серий с разными output roots на одной H100 одновременно.

## Источники и статус проверки

- [NanoWM upstream](https://github.com/simchowitzlabpublic/nano-world-model), закреплённый backbone `cc1f151a9d8c7d7afd0cdc5de6a9ae220a7c90c0`.
- [XLand upstream](https://github.com/dunnolab/xland-minigrid), симулятор `0d306d1414dcb6e451358d94e7d9a91879462ee1`.
- [Upstream benchmark loader/registry](https://github.com/dunnolab/xland-minigrid/blob/0d306d1414dcb6e451358d94e7d9a91879462ee1/src/xminigrid/benchmarks.py).
- Приложенные PDF: план экспериментов (14 стр.), Nano World Models (19 стр.), Video Action Models летней школы (7 стр.), XLand-MiniGrid (27 стр.). Отчёт летней школы использует другое окружение ShapeCraft, frozen VAE и action head; опубликованных исходников этого расширения пользователь не предоставил.

Проверка новой реализации: Python compile, bash syntax и 15 проверок контрактов прошли на Python 3.11 / torch 2.7.1 / JAX 0.4.38. Проверки не выполняют optimizer steps и не запускают PPO/WAM обучение. Проверены native simulator, точная длина задач, semantic split, полный сбор и replay датасета, objectives/masks, сдвиг действий, inference без будущих ответов, counterfactual pairing, визуальная task cost на идеальных кадрах, правила resume и запрет обучения на локальном Mac.

Настоящий исторический файл прочитан с проверкой SHA256: 1 000 000 строк; для выбранных трёх типов целей подходят 245 996 строк и 1 890 уникальных канонических групп. Для каждого depth=1/2/3 проверен полный банк основного конфига: 192 train + 24 val + 48 test, точная достижимость и отсутствие более короткого решения. Визуальный контроль с настоящими идеальными будущими кадрами прошёл 264/264 для каждой глубины. Это диагностический oracle-контроль, **не SR обученной NanoWM**. В загрузчике учтены исторические `num_rules` формы `[N,1]` и int32 goal encodings.

Эта проверка выявила и исправила две ошибки task cost: усреднение координат похожих серых объектов могло поместить предмет в несуществующую клетку; плавное сходство пикселей кармана давало положительный прогресс за взятие неверного похожего предмета. Теперь положение выбирается как дискретная клетка, а содержимое кармана сопоставляется с типами и цветами предметов. Регрессия включена в тесты. Это пример причины низкого SR, не связанной с обучением модели.

Обучение на H100, BF16 backend, установка полного серверного окружения и достижение SR100 должны быть фактически проверены на сервере указанными командами. Старые CPU-результаты из `reports/` к этим заявлениям не относятся.
