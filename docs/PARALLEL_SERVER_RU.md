# Параллельный запуск девяти моделей на H100

Запускается одна серия: `policy`, `video`, `joint` с горизонтами 1, 3, 5,
seed 3407. Дополнительные сравнения на 128/512 сценах сюда не входят.

На описанном сервере одна H100 80 ГБ. `JOBS=3` означает три независимых
эксперимента одновременно на первой видимой CUDA GPU. Это не три видеокарты
и не распределённое обучение одной модели.

## Устройство запуска

1. Один процесс готовит банк, обучает PPO, собирает RGB, кодирует VAE и
   выполняет диагностический визуальный контроль. Эти данные общие для всех моделей.
2. Подготовительный процесс завершается и освобождает свой CUDA-контекст.
3. Координатор запускает до `JOBS` независимых процессов. Каждый обучает ровно
   одну модель, со своими RNG, optimizer, checkpoints и логом. Данные читаются
   из общих массивов `.npy` через mmap.
4. Освободившееся место сразу занимает следующий вариант. Сначала идут длинные
   горизонты. Отчёт `summary.md` обновляет только координатор после завершения
   очередной модели.

Координатор не импортирует Torch/JAX и не хранит GPU-тензоры. CPU affinity
устанавливается до импорта ML-библиотек в работнике, чтобы JAX не создавал
полный пул потоков на все CPU для каждой модели. По умолчанию выдаётся до
четырёх доступных CPU на процесс и до двух потоков Torch/BLAS.

На процесс ставится лимит аллокатора PyTorch `0.9 / JOBS` от памяти видимой
GPU: при трёх процессах — 30% каждому. Это верхний предел, а не заранее
занятая память. Служебные CUDA-выделения могут находиться вне этого лимита;
реальный пик нужно смотреть в `nvidia-smi` и runtime отчёте каждой модели.
Описание механизма: [PyTorch](https://docs.pytorch.org/docs/stable/generated/torch.cuda.memory.set_per_process_memory_fraction.html).

Несколько процессов могут перекрывать работу CPU и GPU. Ускорение нельзя
вычислить только из числа процессов: его нужно измерить по времени и загрузке
GPU. Когда GPU уже занята полностью, больше процессов может замедлить работу.
Для совместного исполнения CUDA-процессов существует
[NVIDIA MPS](https://docs.nvidia.com/deploy/mps/index.html). Скрипт наследует
настроенное окружение MPS, но сам не запускает и не меняет системный сервис.

## Запуск после загрузки изменений на GitHub

В SSH-сессии сервера:

```bash
cd ~/myproject/mini-WAM
git pull
mkdir -p logs

JOBS=3 nohup bash scripts/train_server.sh single-goal-parallel \
  > logs/single-goal-parallel-launcher.log 2>&1 < /dev/null &
echo "PID оболочки: $!"
```

Установленное `.venv-server` используется напрямую; активировать его вручную
не требуется. Если окружение отсутствует, сначала `bash scripts/setup_server.sh`.

Новый каталог результатов — **`runs/server/single_goal_parallel/`**. Старый
`single_goal` остаётся отдельной серией. Изменение серверного кода меняет
`source_sha256`, поэтому старые checkpoints и данные не подмешиваются в новый
запуск. Общий lock output root блокирует одновременный запуск старой
последовательной и новой параллельной серии через этот shell-скрипт.

Небольшая проверка того же механизма, если нужна перед основной серией:

```bash
JOBS=2 bash scripts/train_server.sh single-goal-smoke-parallel
```

Это отдельные маленькие банки, 20 обновлений каждой WAM и настоящий PPO gate;
проверка не заявляет сходимость WAM. Она пишет в `single_goal_smoke_parallel`.

## Наблюдение

Общий ход подготовки и очередь:

```bash
tail -F logs/single-goal-parallel-latest.log
```

После общей подготовки появляются индивидуальные логи, например:

```bash
tail -F runs/server/single_goal_parallel/job_logs/video_n5_seed3407-latest.log
tail -F runs/server/single_goal_parallel/job_logs/joint_n5_seed3407-latest.log
```

В другом SSH-терминале:

```bash
watch -n 3 nvidia-smi
```

Состояния всех девяти работ, PID и пути логов:

```bash
.venv-server/bin/python -m json.tool \
  runs/server/single_goal_parallel/parallel_status.json
```

`parallel_status.json` появляется при запуске моделей. Во время подготовки
работает один процесс, поэтому трёх обучений в `nvidia-smi` ещё не будет.

## Остановка, ошибка и продолжение

В общем логе строка `КООРДИНАТОР: PID=...` содержит PID для остановки:

```bash
kill -TERM <PID_КООРДИНАТОРА>
```

Координатор завершает активных работников вместе с их дочерними процессами.
Продолжение использует последние сохранённые checkpoints; обновления после
последнего checkpoint могут потребовать повторения.

При ошибке работника очередь останавливается, остальные активные работники
завершаются, новые не запускаются. Причина находится в индивидуальном логе,
состояния сохраняются в `parallel_status.json`. При нехватке CUDA-памяти
повторите **тот же запуск с меньшим `JOBS`**:

```bash
JOBS=2 nohup bash scripts/train_server.sh single-goal-parallel \
  >> logs/single-goal-parallel-launcher.log 2>&1 < /dev/null &
```

При том же коде и конфигурации готовые стадии/модели проверяются и пропускаются,
незавершённые продолжаются. Изменять batch для уменьшения числа процессов не
нужно. Число работников и CPU-ресурсы не входят в научную конфигурацию модели.

После завершения:

- `summary.md` / `summary.json`: SR всех девяти вариантов;
- `diagnosis.json`: проверки качества и причины неуспеха;
- `models/<mode>_n<horizon>_seed3407/`: веса, оценки и видео;
- `job_logs/`: отдельные логи каждого запуска модели;
- `parallel_status.json`: состояние очереди и коды выхода процессов.

Код 0 всего запуска означает завершение с требуемым SR100. Код 2 означает,
что все модели отработали, но SR100 достигнут не везде. Техническая ошибка
возвращает другой ненулевой код. Число одновременно работающих моделей не
меняет критерий SR и не означает, что он уже достигнут.

## Проверка реализации

Локальные проверки запускают короткие фиктивные CPU-процессы и проверяют
реальное перекрытие трёх работ, предел параллелизма, отдельные логи, остановку
очереди, обработку ошибок, порядок подготовки и итоговый код SR gate. Обучение
PPO/WAM локально не запускается. Память и ускорение именно на H100 требуют
фактического серверного прогона.
