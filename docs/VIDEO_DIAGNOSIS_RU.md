# Просмотр и следующий шаг для video

> Этот документ разбирает прежний `one_step` возле цели. Текущая постановка с
> несколькими перемещениями, чистым рендерером и горизонтами 1/3/5 описана в
> [новом плане](SINGLE_GOAL_RU.md). Старые веса нельзя считать её решением.

Скачанные веса и исходные метрики остаются прежними. Нового обучения на Mac нет.
Галерея строится обычным Python без torch/JAX и читает существующие PNG/MP4.
При переносе папки с результатами повторно выполните `scripts/view_results.py`,
чтобы пересоздать относительные ссылки.

## Что уже установлено по сохранённым результатам

На validation video решает 9/24: взять предмет — 3/8, подойти — 5/8,
положить рядом — 1/8. При подаче идеальных настоящих будущих кадров тот же
визуальный критерий решает 24/24, после VAE-реконструкции — 20/24.
В четырёх неудачных реконструированных сценах видны равные оценки нескольких
действий, часто нулевые. `argmax` выбирает первое из них, что не гарантирует успех.

В video прогнозы реагируют на действия: на test их latent MSE составляет
0.001376, при изменённых действиях — 0.002773, при копировании контекста —
0.001737. Это полезный сигнал, но он не подтверждает правильность каждого
предмета, кармана и решения планировщика.

У joint test SR=100% обеспечивается action head. Её test latent MSE=0.002380
хуже копирования 0.001737. Поэтому вопрос качества будущих картинок у joint
также остаётся открытым, несмотря на успешное управление.

Старые offline-метрики генерации вычислялись на первых восьми из 64 выбранных
окон. На test это эпизоды `[0,5,10,15,21,26,31,37]`, и ни в одном агент не
меняет координаты. Поэтому полученные ADE/FDE=0 не доказывают освоения движения.
Новая диагностика рассматривает все шесть действий для каждой validation-сцены,
включая движение и взаимодействия с предметами.

## Что делает диагностический запуск

```bash
bash scripts/train_server.sh diagnose-video
```

1. Проверяет хеш существующего `video_n1_seed3407/best.pt` и загружает его.
2. Берёт только validation: исходный test не используется для настройки нового критерия.
3. Для каждой сцены сохраняет настоящие последствия всех шести действий,
   реконструкции VAE и прогнозы замороженной NanoWM с одинаковым noise для кандидатов.
4. Сравнивает пять контролей: настоящие RGB со старой стоимостью; реконструкции
   VAE со старой стоимостью; настоящие encoded futures с новой стоимостью;
   прогноз NanoWM со старой и новой стоимостью.
5. Сохраняет все оценки кандидатов, выбранные действия, правильность выбора,
   contact sheets и анимации «исходное наблюдение → следующий кадр».

Новая стоимость сравнивает предсказанный латент с латентами возможных картинок
цели. Цель задаётся публичной RGB-панелью: предмет в кармане, агент рядом с
предметом либо два соседних предмета. Для соседства допускаются все свободные
соседние клетки. Эти картинки строятся из текущего RGB, без знаний о том,
какое действие к ним приводит. Действия всё ещё должен различить NanoWM.
Для изменившихся областей используется фиксированный вес `1+4*ROI`.
Функция стоимости не принимает simulator state, action IDs или success labels.

Это новая абляция для данной одношаговой observable-goal постановки. Она не
является воспроизведением скрытой meta-RL задачи XLand или action head из отчёта.
Успех нового критерия нельзя объявить заранее: его должен показать серверный отчёт.

Исходные веса и файлы оценки не перезаписываются. Диагностика пишет отдельную
папку `runs/server/one_step_video_diagnostic`, поэтому ей не требуется resume
старого training run с изменённым source hash. Для быстрого ручного прогона
двух validation-сцен можно использовать CLI с новой папкой:

```bash
.venv-server/bin/python -m miniwam.server diagnose-video \
  --run runs/server/one_step --out runs/server/video_diagnostic_preview --limit 2
```

GIF создаются через Pillow без запуска ffmpeg из процесса JAX.

## Что делать по результату

- Если новый критерий ошибается даже на настоящих encoded futures, сначала
  исправить представление цели или метрику. Обучение NanoWM это не проверяет.
- Если этот контроль даёт 100%, а прогнозы NanoWM дают существенно меньше,
  изучить именно неверные предсказанные взаимодействия: исчезновение предмета,
  появление в кармане, размещение рядом. Точность статичного фона недостаточна.
- Если новый критерий улучшает выбор на validation, зафиксировать его и выполнить
  отдельную итоговую test-оценку. До этого исходные 27.1% остаются единственным
  измеренным test SR video; новые validation-числа их не заменяют.
- Если предсказания требуют дообучения, следующий training run должен иметь новый
  output root, проверку качества предметов/кармана и сравнение с исходным checkpoint.
  Увеличение бюджета без этой диагностики само по себе не объясняет текущие ошибки.

Локально проверяются построение RGB-целей, соответствие настоящим успешным
переходам и работа диагностического runner на тестовых замороженных прогнозах.
Вызов настоящего NanoWM и измерение нового validation SR выполняются на сервере.
